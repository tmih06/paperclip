# Node versus Bun: production API runtime

## Result

On this host, switching the same production server bundle from genuine Node
24.18.0 to Bun 1.4.4 reduced median startup time by **30.4%** and idle
main-process RSS by **22.2%**. At 16 concurrent requests, throughput increased
by **25.6–46.1%**, depending on the route; p95 latency decreased by
**25.2–29.3%**. Single-request health p95 did not improve.

This isolates runtime selection, not every change in the migration. It does
not measure AI-provider execution, browser rendering, or the live deployment.
No application optimization was made for this experiment.

## Setup

- Measured revision: `2a9e4697c4c0e8ca1636bdc4f90450c874cfd992`.
- Build metadata: `8346cdb5c0e8c2bb4aedc42763a9c80657de5a3d`. No server,
  package, manifest, or lockfile changes occurred between that build revision
  and the measured revision; the intervening changes are docs and this harness.
- Both runtimes executed the **same** `server/dist-runtime/index.mjs` production
  bundle, generated by the existing `build:runtime` command also used by Docker.
  All 173 JavaScript bundle-file digests and the lockfile digest are recorded
  in the [raw results](2026-11-17-node-versus-bun.json).
- Linux ARM64, four logical CPUs, approximately 23.4 GiB RAM. The CPU reports
  ARM implementer `0x41`, part `0xd0c`; the OS runtime's model name is `unknown`.
  Kernel: `7.0.0-1013-oracle`.
- The server and its embedded PostgreSQL children were restricted to CPUs
  `0,1`; the identical Bun HTTP load generator used CPU `2`. This is affinity,
  not dedicated/exclusive CPUs: other host services continued to run.
- Each server received a clone of one initialized, cleanly stopped disposable
  database: one company, 100 unassigned backlog tasks, **zero agents**.
- Loopback only; production mode; UI disabled; telemetry, announcements,
  heartbeat scheduling, and database backups disabled identically. Normal
  application middleware and database-backed API routes remained enabled.
  No live database, deployment, provider, host-isolation setting, or runtime
  installation was modified.

An initial compatibility probe found that Node cannot directly run the
workspace's unbundled `server/dist/index.js`: workspace exports resolve to
TypeScript sources with `.js` import specifiers. The existing Docker runtime
bundle resolves this without adding a Node-only loader. Failed probes and
one-second pilot timings are **not** included in the results below.

## Method

Five paired trials, alternating order: Node/Bun, Bun/Node, Node/Bun, Bun/Node,
Node/Bun. Startup measures process launch to the first healthy `/api/health`
response, polling every 50 ms, against an already initialized database with
warm filesystem caches. Database creation/migrations and directory copying
are outside the startup measurement; embedded PostgreSQL startup is inside it.
Idle RSS is sampled two seconds after readiness, before route validation/load.

Each trial then runs health, company listing, and a 50-task listing, in that
order, first at concurrency 1 and then at concurrency 16. Each workload has
three seconds of warmup followed by eight measured seconds. HTTP/1.1
keep-alive connections fully consume responses; there is no TLS, HTTP cache,
conditional request, browser, or external network hop. Requests begun during
the measured window retain their full latency even if they complete after the
deadline; throughput includes that final drain time.

Values below are **medians of five trial-level measurements**. The latency
columns are medians of trial percentiles, not pooled-request percentiles.
Changes are ratios of medians. All **276,697 measured requests** returned
HTTP 200: 118,072 for Node and 158,625 for Bun. Request errors or changing
response lengths fail the harness. Company and task-list response digests
also matched across all ten server instances.

## Startup and memory

| Metric | Node | Bun | Change |
|---|---:|---:|---:|
| Time to healthy API | 7.265 s | 5.059 s | 30.4% shorter |
| Idle server RSS | 583.3 MiB | 453.8 MiB | 22.2% lower |
| Server RSS during final task-list load, c16 | 1,015.6 MiB | 673.9 MiB | 33.6% lower |
| Sampled peak RSS in that final phase | 1,033.4 MiB | 776.7 MiB | 24.8% lower |

Startup ranges were 7.183–7.612 s for Node and 4.897–5.276 s for Bun. Idle
RSS ranges were 577.9–587.6 MiB and 451.8–454.2 MiB, respectively.

RSS is for the **main server process only**, not PostgreSQL, children, the
load generator, or the entire machine. Loaded RSS is sampled every 100 ms;
shorter peaks can be missed. It includes heap retained from earlier workloads,
so it is not an isolated per-route allocation measurement or a long-run leak
test. Bun served more requests during the same elapsed workload time.

## CPU

These are main-process CPU utilization medians over **warmup plus load**;
100% means one logical CPU. They exclude database and load-generator CPU,
and must not be interpreted as total host cost or an equal-request-count
CPU benchmark. Bun is doing more work in the same elapsed time.

| Route, c16 | Node server CPU | Bun server CPU |
|---|---:|---:|
| Health | 106.1% | 109.2% |
| Companies | 101.9% | 99.4% |
| Tasks, 50 rows | 78.9% | 74.7% |

The load generator never exceeded 28.9% of its assigned logical CPU. Its
CPU consumption is recorded separately for every phase. No CPU profiles were
collected; the gains have not been apportioned between engine execution,
garbage collection, and runtime I/O compatibility.

## Reproduce

From a checkout with dependencies and production server outputs built:

```sh
bun run --filter @paperclipai/server build:runtime
bun test scripts/benchmark-js-runtime.test.mjs
bun scripts/benchmark-js-runtime.mjs \
  --baseline="$(command -v node)" \
  --runs=5 --seconds=8 --warmup=3 \
  --app-cpus=0,1 --client-cpus=2 \
  --output=/tmp/paperclip-runtime-comparison
```

Use a genuine Node 24.18.0 executable for an exact runtime comparison. The
orchestrator checks that the baseline is not Bun aliased as Node. It creates
only temporary state and random loopback listeners, records per-instance logs
and JSON results in the output directory, and stops its process groups and
removes its database clones afterward. Neither runtime is installed or changed.

## Limits

This is a short, closed-loop local API benchmark on one shared ARM host,
not a complete production capacity study. It does not establish cold-cache or
first-install performance, sustained memory growth, fixed-arrival-rate p99
latency, write throughput, authenticated multi-tenant behavior, WebSockets,
UI responsiveness, build/test/install speed, or AI-provider execution speed.
The fixed workload order can affect JIT and heap state. Those paths need their
own measurements before claiming the entire application is faster by one
percentage. No deployment was performed and no performance tuning was applied.
